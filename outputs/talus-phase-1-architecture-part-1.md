# Talus — Phase 1 Architecture, Part 1

**Status: proposed architecture for review.** Based on the complete *TALUS — BUILD INSTRUCTIONS (MVP V1, DOC V2)*, including §§1–35 and §§19A, 30A. Section references below refer to that source. Technical documentation was checked on September 3, 2026.

This part covers the recommended stack, the complete V1 logical data model, and the database implementation of the two guarantees in §4. It contains no application code, database DDL, migration scripts, HTML, or setup commands. Lifecycle transition matrices, detailed module contracts, the dependency graph, and build order remain for the next review stage. Instructions in the attachment to proceed through a broader build do not expand the scope of this request.

The central recommendation is **one PostgreSQL system of record, one versioned API, category commitments without early machine assignment, and a separate database-constrained machine occupancy relation**. Financial agreements and operational evidence are preserved as immutable revisions. Every material mutation is inseparable from its unified audit record.

## 1. Recommended technology stack

### 1.1 Stack and responsibilities

| Layer | Recommendation | Reason for this system |
| --- | --- | --- |
| Database | Managed PostgreSQL 18, with `btree_gist` and PostGIS | Transactions, composite foreign keys, row-level security, exact integer arithmetic, range exclusion constraints, and spatial queries cover Talus's central integrity requirements in one database. Require backup and point-in-time recovery support from the eventual host. |
| Public API | TypeScript, Node.js 24 LTS, Fastify, a versioned REST/OpenAPI contract | A single external entry point handles authentication, validation, rate limits, response contracts, and provider adapters. Node 24 is an LTS release; Fastify supports request and response schemas. Neither layer decides database permissions or independently recalculates booking rules. [Node release policy](https://nodejs.org/en/about/previous-releases), [Fastify validation and serialization](https://fastify.dev/docs/v5.8.x/Reference/Validation-and-Serialization/). |
| Database access inside the API | Private PostgREST service exposing a deliberately small, versioned function schema | Provides verified JWT-to-database-role propagation and a transaction per request. Expose named operations rather than generic table CRUD. It is an internal component of the single Talus API, with no separate interface-facing endpoint. [PostgREST authentication](https://postgrest.org/en/stable/references/auth.html), [transaction context](https://postgrest.org/en/stable/references/transactions.html). |
| Authoritative business operations | PostgreSQL functions with narrowly scoped execution privileges | Pricing, availability, commitment changes, assignment, occupancy, lifecycle enforcement, and financial posting execute once, near their constraints, within a transaction. The API and workers invoke those operations rather than maintaining alternative implementations. |
| Interfaces | React and TypeScript for the operator app and shared customer booking experience | The widget embeds the same booking experience served by the standalone site. Both consume the same API contract. Interface state never becomes authority for prices, inventory, or permissions. |
| Authentication | Managed OIDC for staff; scoped customer sessions; separate device credentials; short-lived signed API identity tokens | Staff, customers, devices, and internal workers have distinct identities and permissions. A customer does not need a general-purpose account or rider-management subsystem. |
| Background work | Node workers consuming a transactional PostgreSQL job/outbox model | Assignment scheduling, message sending, provider reconciliation, and telemetry processing can retry safely. Jobs retain tenant and initiating-actor context. A second booking database, webhook synchronization system, or separate availability cache is unnecessary. |
| Files | Private object storage with immutable object versions and database metadata | Stores inspection photos, incident attachments, and signed document artifacts. All access authorization occurs through the API and tenant-scoped metadata. Storage credentials are never browser credentials; file content is not overwritten in place. |
| Telemetry and maps | PostgreSQL event records, partitioned raw frames, PostGIS geometry, an API-fed map interface | Keeps measured evidence connected to permanent Trip identities. PostGIS supports spatial boundary evaluation; using a boundary-inclusive predicate avoids treating a point exactly on a fence as outside. [PostGIS boundary semantics](https://postgis.net/docs/manual-3.7/en/ST_Covers.html). |
| Verification, after architecture approval | Real PostgreSQL integration tests, API contract tests, and browser workflow tests | Required security and concurrency properties must be tested using production-equivalent roles and constraints. Mocked repositories cannot establish those guarantees. No tests or implementation are written in this phase. |

Payment, tax, email, and SMS providers remain replaceable adapters. The payment processor and timing policy remain founder decisions under §35. A tax provider is intentionally not selected. For SMS, recommend a tenant-specific sending identity in V1 to make routing and opt-out ownership unambiguous; carrier registration and consent remain distinct configuration and operational concerns.

### 1.2 Data-layer multi-tenancy: §28

Every tenant-owned row carries a required `tenant_id`. Its primary key includes that tenant identifier, and every relationship to another tenant-owned entity uses a composite foreign key containing the same identifier. A booking item cannot reference another tenant's booking, machine, price revision, or Trip even if application code supplies a valid foreign UUID.

Enable and force row-level security on every tenant-owned relation, including raw telemetry, evidence metadata, audit, idempotency, and jobs. Policies default to denial when identity or tenant context is missing. Runtime roles never own tables and never have superuser or `BYPASSRLS` privileges. PostgreSQL explicitly distinguishes ordinary policy enforcement from the privileges that bypass it; forcing RLS does not neutralize a superuser. [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html).

Tenant isolation and authorization within a tenant are separate checks. Staff can access tenant operational records according to their role. Customers can access only their authorized booking/session and waiver resources. Devices can submit frames for their own registered device binding, and cannot read bookings, change configuration, or perform staff actions.

Catalog and availability reads need a deliberate policy. Customer callers may access published catalog data and non-personal scheduling facts for their verified tenant context. They do not gain access to customer contact details, other bookings, or machine identifiers in API responses. Scheduling facts are separated from personal booking data in the model below; availability uses those facts under the customer's actual RLS policy, without switching to an administrative reader.

Onboarding inserts a tenant, its initial policies, locations, and memberships through an internal audited operation. It does not create a database, schema, or role per tenant.

### 1.3 Identity propagation and the API boundary: §30A

The API validates the external credential and obtains a short-lived, signed identity token containing subject, caller class, permitted tenant context, session identifier, audience, and expiry. Private PostgREST verifies the token and applies its allowlisted database request role and claims for the transaction. PostgreSQL policies resolve current membership, session validity, device status, and resource scope from database records.

Staff tenant selection must match an active membership. Customer browsing context comes from a registered embed installation or standalone-site configuration exchanged for a scoped session. A hostname can locate configuration but cannot establish authority. A customer-supplied tenant header, body property, or arbitrary database role name never establishes identity. Device tenant and device identity come from its registered credential, not the telemetry payload.

The public API process has no database superuser, table-owner, or generic SQL credential. The private PostgREST authenticator can assume only the allowlisted request roles, not command-owner or maintenance roles. No RPC permits arbitrary SQL, role switching, or modification of the authenticated request claims. Claims are transaction-scoped, including on pooled connections; missing, empty, expired, or stale session context fails closed. These boundaries prevent a custom session variable from becoming a client-controlled substitute for authentication.

Provider callbacks are authenticated by the eventual provider adapter and mapped to the registered tenant payment or messaging account identified in the verified event. Processing then uses a scoped service Principal under RLS. Neither a callback's unverified tenant field nor a generic cross-tenant service credential supplies that authority. Reserving a distinct future integration caller class does not create an integration API in V1.

Read functions use invoker privileges. Any read views use invoker security as well; PostgreSQL views otherwise commonly evaluate permissions and RLS as their owner. [PostgreSQL view security](https://www.postgresql.org/docs/18/sql-createview.html). An owner's page in the operator app still executes under that owner's actual tenant membership. Reports have the same rule.

Use one external contract: versioned endpoints; an error envelope containing a stable error code, error category, safe message, request ID, retryability, and relevant field details; bounded cursor pagination; allowlisted filters and sort fields; and a stable unique tie-breaker for sorting. Rule conflicts, permission denial, validation errors, and system failures are distinct. Overbooking warnings include a review token tied to the proposed operation and observed capacity, never permission to skip revalidation. Old supported widget versions continue using their API version. This is a V1 product API, not a partner API or webhook publishing platform.

### 1.4 Function-only writes and unified audit: §§30–31

Request roles have **no direct table insertion, update, deletion, truncation, object-creation, or privilege-management rights**. They receive execution rights only for the named operations their caller class needs. Examples of operations are Confirm booking, Modify booking, Extend rental, Assign machine, Override assignment, Record return, Post payment result, Record inspection, and Change operating limits. These are architectural operation names, not implementation signatures.

Mutating functions require controlled privilege elevation because callers cannot write tables. Each is owned by a dedicated non-login role with only the necessary table privileges, no ownership of those tables, and no RLS bypass. Its RLS policies still evaluate the original verified actor and tenant claims; changing the function's effective database user must not replace the human or device identity. Sensitive functions independently require the current database-recorded role, with manager or owner required for rate changes, fleet-state changes, deposit capture, and customer warning/do-not-rent changes. Recommend the same threshold for intentional category overbooking and manual assignment overrides.

Use a fixed trusted function search path, fully qualified database objects, no client-controlled dynamic SQL, and explicit execution grants. Revoke PostgreSQL's default public function execution rights. These are essential controls for security-definer functions. [PostgreSQL function security](https://www.postgresql.org/docs/18/sql-createfunction.html).

Each material operation creates an immutable `AuditEvent` in the same database transaction as its effects. Database write guards require an authorized operation context and connect affected rows to that operation; a successful domain change cannot commit if its audit append fails. This combines a useful business event with database enforcement against an accidentally unaudited write. Multi-row changes share an operation ID and can have multiple ordered audit events. Retries return the earlier operation result rather than repeating its financial or operational effects.

The audit record contains tenant, actor, caller class, action, affected entity identifiers, database timestamp, operation/request IDs, reason, relevant before/after facts or immutable revision references, and originating staff identity for automated follow-up work. Audit details exclude passwords, bearer tokens, full card data, and unnecessary raw telemetry. Telemetry frames remain their own evidence records; ingest acceptance, corrections, violations, and consequential actions use the same audit architecture rather than copying every signal into the audit log.

Append-only tables have neither update nor delete privileges for runtime roles, plus mutation-rejection guards. Corrections add compensating entries or superseding revisions. This protects against application mistakes and compromised ordinary application credentials; it does not pretend a database owner or infrastructure administrator is cryptographically incapable of altering storage.

**Enumerated exceptional infrastructure paths:** schema maintenance, tenant bootstrap, backup/restore, and retention administration. They use separate internal identities, narrowly scoped operations, and durable administrative audit records. Any table-owner or bypass credential is absent from the request-serving environment and unreachable through external API routes. Routine assignment, payment callbacks, notifications, and telemetry workers use tenant-scoped identities and ordinary RLS; they are not exceptions. Restore administration records its actions outside the database being restored as well, so restoring an earlier backup cannot erase the sole record of that action.

### 1.5 Exact financial arithmetic and time

All stored monetary amounts are signed 64-bit **integer cents**; a field's business meaning determines whether negatives are allowed. All percentages are **integer basis points**. Discounts, refund percentages, and commissions are bounded from 0 to 10,000 basis points. Taxes and fees have nonnegative, validated bounds appropriate to the configured policy. There are no floating-point operations in quoting, pricing, tax conversion, discounts, ledger posting, refunds, or reconciliation.

Use integer multiplication and quotient/remainder arithmetic, with exact widened intermediate values to prevent overflow before division. Every result is range-checked before being stored as cents. PostgreSQL's exact integer and numeric types support this distinction from floating-point types. [PostgreSQL numeric types](https://www.postgresql.org/docs/18/datatype-numeric.html). APIs serialize potentially large monetary integers as decimal strings; TypeScript treats them as exact integers, never JavaScript `Number` values. Currency display also avoids floating-point conversion. Provider decimal amounts must be parsed from exact text into cents and validated.

Each price revision records its calculation version, operation ordering, rounding rule, tax basis, and allocation method. Recommend rounding each specified charge component once to cents using an explicitly versioned rule, and allocating aggregate discounts deterministically by integer remainders. Refunds reverse the recorded allocations. Provider- or jurisdiction-specific rounding requirements can replace the proposed rule without changing old revisions.

Store an IANA timezone, local rental dates, scheduled pickup/return instants, and the agreed chargeable calendar-day count. **Calendar-day pricing and physical occupancy use different representations.** Pricing counts local calendar dates using the snapshotted date-counting convention, never elapsed timestamp hours divided by 24. Occupancy uses actual instants. The source does not settle whether a return date itself is billable; preserve that as an explicit review decision rather than silently selecting inclusive or exclusive billing. Ambiguous daylight-saving local times require an explicit resolved offset.

## 2. Complete V1 logical data model

### 2.1 Conventions and universal constraints

In the catalog below, **T** means `tenant_id`. Unless a different key is stated, an entity has primary key **(T, id)** and a foreign key from T to Tenant. Every arrow denotes a **same-tenant composite foreign key**, not an unscoped UUID relationship. A child keyed by its parent uses that parent's same-tenant key. Natural uniqueness rules are tenant-scoped unless explicitly identified as infrastructure identity uniqueness.

All required references and invariant fields are non-null. Optional references are identified as optional; a missing value is not replaced with a made-up entity or zero. Every mutable operational root has a revision number for optimistic concurrency. Creation time and creating actor are server-controlled. Immutable revisions include their parent, sequence number, recorded time, actor, and content hash where evidence integrity matters. Sequence numbers are unique within the parent; the first predecessor is null, and later predecessor references must remain within that parent and form a single ordered revision chain. Creation pointers that form a parent/revision cycle are checked at transaction commit, not bypassed by nullable confirmed records.

Deletion of referenced historical entities is restricted. Customers, categories, locations, machines, devices, staff identities, and policies are disabled or retired rather than cascade-deleted. Historical display labels, contact details, terms, location/category identity, and device capabilities are captured where applicable. A foreign key to a mutable catalog record alone is not a historical snapshot.

Row checks enforce local value rules; unique and exclusion constraints enforce structural uniqueness; foreign keys enforce relationships. Cross-row requirements use database constraint triggers or named functions with the required locks. They must not be represented as ordinary row checks that purport to query other rows safely.

Where a row references both a parent and an ancestor, same-tenant FKs are necessary but not sufficient: the parent must actually belong to that ancestor. Use an additional composite candidate key containing the ancestor, or a deferred database ownership check. This applies particularly to booking/item/revision links, Trip/evidence/summary links, payment/booking/item allocations, and waiver flow/request/participant coverage. Counters and current-revision pointers are checked against their immutable source records at commit.

### 2.4 Booking, commitments, assignment, and lifecycle data

**One BookingItem represents one rentable unit.** A customer choosing three UTVs creates three items, which may be grouped into one visual order line. It does not create one operational item with quantity three. This makes independent assignment, inspection, checkout, return, incident handling, and closure possible (§6).

| Entity | Keys and relationships | Required content and constraints |
| --- | --- | --- |
| Booking | PK (T, id); customer → Customer; pickup/return locations → Location; current terms → BookingTermsRevision; state → LifecycleState | Unique tenant booking reference; currency; lifecycle version and current state. At least one item is required for confirmation. V1 requires pickup and return locations to be equal. No stored independent payment balance or message-sent flag. |
| BookingTermsRevision | PK (T, id); booking → Booking; predecessor → same booking's revision; configuration → TenantConfigurationVersion | Unique booking revision number; agreed customer contact details, location names/identities, operational and cancellation terms, timezone, reason, actor, and agreement time. Immutable. A later Customer edit or tenant policy change cannot rewrite this revision. |
| BookingItem | PK (T, id); booking → Booking; current terms → BookingItemTermsRevision; state → LifecycleState | Unique item number within booking; independent operational state and version. Quantity is structurally one. No independently editable machine pointer: current assignment comes from occupancy. |
| BookingItemTermsRevision | PK (T, id); item → BookingItem; booking terms → BookingTermsRevision; offering → CategoryLocation; predecessor → same item's prior revision | Category and location identity/name snapshots, local start/return dates, scheduled pickup/return instants, calendar-day count, rate-version reference, revision number. Scheduled return is later than pickup; day count is a positive integer calculated under the stored convention. The booking-terms and item references must resolve to the same booking. |
| CategoryCommitment | PK (T, item_id) → BookingItem; item terms → BookingItemTermsRevision | Canonical current reservation claim, with held/committed kind and optional hold expiry. Dates/category/location are obtained from the referenced item terms, not copied into another editable calendar. Exactly one current claim per consuming item; expired holds do not count on read. No machine reference and no available-count field. |
| BookingAddOnSelection | PK (T, id); booking terms → BookingTermsRevision; optional item terms → BookingItemTermsRevision; add-on/rate → AddOn and AddOnRateVersion | Positive integer quantity, selected charging basis, immutable description and selection terms. Item-scoped selections must belong to the same booking revision. |
| AssignmentAttempt | PK (T, id); item → BookingItem; operation → OperationRecord; optional proposed machine → Machine | Automatic/manual origin, result, timestamp, and structured failure reason. Failed assignment records contain no fictional successful machine. Success references the resulting occupancy. A committed item needing assignment with no valid occupancy is also discoverable directly on read. |
| MachineOccupancy | PK (T, id); machine → Machine; either item/item terms → BookingItem/BookingItemTermsRevision, or block → MaintenanceBlock | Kind restricted to rental or maintenance; exactly one appropriate owner. Required nonempty half-open occupancy range; blocking status; origin and release audit references. At most one blocking rental occupancy per item. All blocking rental and maintenance rows share the same machine/range exclusion constraint described in §3. |
| CheckoutOccurrence | PK (T, id); item → BookingItem; occupancy → MachineOccupancy; initiating staff → Principal | Unique (T, item, checkout ordinal); frozen machine/device binding and preparation identity for a particular departure. Provides an inspection/boundary anchor before a Trip opens. It is not a separate customer-arrival lifecycle or a motion-created Trip. |
| LifecycleState | PK (entity kind, state code, definition version), global read-only reference data | Separate state domains for Booking and BookingItem, with terminal and commitment-consumption attributes. Initial vocabulary follows §6; naming and exact semantics are reviewed with the later transition matrices. |
| LifecycleTransitionDefinition | PK (entity kind, definition version, from state, to state); both states → LifecycleState | The data definition needed to reject an illegal transition, with fixed authorization/guard identifiers. This is the schema concept only; no legal-transition matrix is supplied in Part 1. It is not a tenant-programmable rules engine. |

Database guards ensure the current revision belongs to its owning booking/item, item location matches the booking's V1 location, occupancy matches the relevant item revision, and active checkout has a matching Trip and physical occupancy. Closing a booking requires every item to be terminal and its required financial/operational conditions to be satisfied; returned alone is not financially closed. Cancelled/no-show terminal semantics and modification permissions belong in the later transition review. State writes already require those database-defined transitions; the interface does not decide legality.

Pending-payment capacity must be explicit. Recommend expiring capacity holds while payment is pending, with the technical hold duration reviewed before implementation. A hold is a reservation fact, not stored availability. Payment success after expiry must revalidate capacity through the same operation; it cannot resurrect an expired claim silently. Confirming a booking and queueing its notification occur transactionally, but confirmation remains true even if message delivery later fails.

Balances are calculated from ledger accounts and entries, including the obligations and adjustments created from each agreed price revision. No independent stored booking balance competes with the ledger. A price revision is an agreement; it is not evidence that a payment occurred. Deposit authorization, collection, release, refund, and any expressly authorized capture remain distinguishable. Actual movement posts only when supported by the provider or an explicitly recorded manual financial action. Incident estimates do not initiate automatic charges. These distinctions preserve the processor-neutral design and keep refundable deposits separate throughout §§13–15.

Posting checks also require a provider settlement's allocation total to equal its confirmed amount, entries with item references to belong to the transaction's booking, and refund/reversal sources to belong to the same tenant/account/currency. Thus an arithmetically balanced journal cannot allocate another booking's money or disguise a deposit as rental income. The original snapshot and every later obligation adjustment remain reconcilable to the journals.

**Permanent binding and late data.** Opening records the exact booking, item, customer, category, location, machine, installed device/capabilities, policy, and staff identity. Closing seals the Trip's end time and core record. Later machine transfer, reclassification, retirement, or hardware replacement changes none of those fields.

The requirement that a closed Trip is immutable and the requirement that it accepts late telemetry are reconciled by separating **sealed Trip identity** from **append-only evidence and summary revisions**. Late frames append evidence associations, metric revisions, and episode revisions; they do not reopen the rental, change its checkout/return facts, or overwrite a prior summary. A finalized summary can receive a clearly identified later amendment if further legitimate evidence arrives; the earlier final revision remains available. This is a proposed interpretation of §19A for review.

Trip attribution uses the accepted event time and the authoritative checkout/return intervals already recorded by lifecycle operations. It never creates a Trip by guessing from motion or by retrospectively drawing a window around GPS points. Ingest and checkout/return serialize on the relevant machine/device binding so a race cannot assign a frame using a half-completed lifecycle change. Intervals are start-inclusive and end-exclusive.

For offline frames, use the **installation that was valid when the measurement occurred**, not the device's latest machine attachment at receipt time. Keep the measured machine's stable identity as the machine-side association and the historical Trip as the rental-side association. This interprets §19A's machine-side wording without allowing a hardware swap to attribute an old measurement to the wrong vehicle. If clock quality or installation history cannot establish a reliable binding, preserve the frame as unassigned/quarantined with a reason; never force it onto a Trip.

Ordering uses accepted event time with device session/sequence as a deterministic tie-breaker, while retaining original device time and server receipt time. Clock adjustment is explicit and versioned. Raw identity and receipt facts are immutable from entry; attribution fields can be resolved once from quarantine, then are sealed on acceptance. A subsequently discovered evidence problem adds a TelemetryEvidenceAnnotation and an audited summary revision; it does not silently move an accepted frame between Trips. Event identity/deduplication tombstones are retained without expiry in V1, even after raw-frame deletion, so an old replay cannot regenerate events or violations. This small per-event metadata has a continuing storage cost; raw-payload retention and deduplication retention are deliberately separate.

**Summaries and honesty.** Raw measured speed is required for a speed verdict; possession of GPS coordinates does not imply that the device supports speed. Distance can be reported as observed GPS-track distance when it is actually computed from valid measured positions, with method and coverage stated; an unobserved gap is not estimated. Full-trip distance is unavailable if the available evidence cannot support it. Rental duration comes from authoritative checkout/return facts and is labelled as operational provenance; telemetry-observed duration, if shown, is a separate metric. That avoids relabelling lifecycle time as a hardware measurement.

The three hardware states are preserved throughout: unsupported, supported but unavailable/stale, and measured with timestamp. Limit assessments additionally distinguish incomplete evidence from clean evidence. A monitored threshold crossing can still be reported when other portions of the Trip lack coverage; the gap is retained alongside it.

**One episode, not one violation per frame.** Processing serializes per machine/Trip and limit. It applies the snapshotted entry/re-entry thresholds and hysteresis to event-time-ordered evidence. Frames update the episode through new revisions. Backfill that joins two provisional episodes records an explicit supersession/merge; current counts exclude the superseded identity while earlier summaries preserve what they previously reported. Raw-event deduplication, episode identity, and unique alert keys jointly prevent duplicate violations and alerts.

Operating-limit changes affect new agreements by default. Existing bookings retain their bound policy unless an explicit authorized terms revision adopts a new one; an open Trip's snapshot remains fixed. This gives a precise meaning to the threshold “in force” for that rental and prevents a configuration edit from rewriting past violations. Any different policy for applying safety-limit changes mid-rental should be reviewed explicitly rather than silently introduced.

**Retention.** Booking, sealed Trip, summary, violation, boundary evidence, and associated audit history are retained together. Raw frames, decoded positions, and raw signal rows share the separately approved raw-data retention policy. Raw deletion never cascades into Trips or violations. A retained event identity/hash, summary input provenance, and peak/boundary facts remain; the API reports when full-fidelity source evidence has expired. Unresolved retention policy does not authorize purging raw evidence.

**Required indexes:** tenant-prefixed booking/customer histories; item-by-booking; commitments by category/location and rental range; occupancy range indexes; Trips by booking, item, machine, device, customer, location, category and start time; telemetry by device/machine/Trip and event time; episodes by Trip/type/time; and a spatial index for geofence geometry. Date-range, violation-type, category, location, machine, and customer filters are indexed API queries, not export-and-reconstruct workflows. Current machine position is a read of the latest valid real event with freshness/capability context, not an invented live coordinate.

## 3. Database implementation of the dual guarantee

### 3.1 Different facts, different enforcement

| Fact | Authoritative record | Database rule |
| --- | --- | --- |
| “This customer has reserved one UTV at this location for these dates.” | CategoryCommitment → BookingItemTermsRevision | A transactional capacity decision accepts the commitment. Authorized staff can accept a known shortage with acknowledgement and audit. A machine is not required yet. |
| “This machine is allocated to this rental or maintenance interval.” | MachineOccupancy | Two blocking occupancy intervals for the same tenant/machine cannot overlap. No staff role, override flag, or capacity acknowledgement relaxes this constraint. |
| “This machine is still physically with a customer.” | Live rental occupancy plus the open Trip | Checkout creates exclusive live custody. A scheduled return timestamp does not release it. Only an actual recorded return/handover ends that custody. |

### 3.2 Derived category availability

For a category, location, and requested interval, the database reads current eligible supply, explicit maintenance/unavailability blocks, active category commitments, fixed assignments, and applicable booking-window rules. It counts each unit commitment once, regardless of whether a machine has already been assigned. Subtracting both the commitment and its assignment would double-count the same rental.

Compute a time-segment capacity profile at the interval boundaries where supply or demand changes. Supply excludes ineligible machines and maintenance blocks; demand includes committed rentals and unexpired holds. A returned machine is no longer physically occupied, but any agreed scheduling commitment is changed only through the authorized operation. Unreturned overdue machines are treated as unavailable with unresolved return time. For a rental that is not overdue, its scheduled return is the planning fact used for later category reservations; it is never permission to end physical custody.

The minimum free capacity over those segments is an upper bound. **Daily counts alone are insufficient when machine eligibility is fragmented.** For example, with two machines, one blocked Tuesday and the other blocked Monday, one unit appears free each day, but neither can serve one Monday–Tuesday item. Before reporting a positive bookable quantity, the same database availability function checks whole-interval feasibility using a fixed, deterministic assignment-feasibility calculation for the relevant overlapping commitments. Existing valid assignments remain fixed; flexible commitments can be matched to eligible machines for their entire intervals. This is a temporary calculation, not an actual early machine assignment or a generalized scheduling platform.

The reported quantity is the largest additional whole-unit demand that fits the applicable commitments and eligibility constraints. If already accepted overbooking makes the relevant overlapping schedule infeasible, report zero normal bookable capacity and a staff-visible shortage. Shortages in unrelated date/location/category components do not erase availability everywhere. Preserve a signed internal shortfall separately in the response; never publish negative inventory as an ordinary customer option. If the feasibility computation cannot complete reliably, return an explicit unavailable-to-quote error, not a guessed positive count.

There is **no availability table, materialized inventory count, or cached value accepted as booking authority**. Catalog descriptions may be cached, but current availability is recomputed on read and again under lock when accepting a commitment. Dates outside the configured booking window return “call us,” with no fabricated open/booked verdict.

### 3.3 Concurrent acceptance and deliberate overbooking

The commitment operation locks the relevant CategoryLocation rows in a stable order, then recomputes availability from the current committed database state. Every operation that changes relevant supply or demand follows the same locking discipline: booking creation, hold acquisition/release, modification, extension, cancellation, maintenance blocking, machine state change, transfer, and reclassification. Cross-category or cross-location changes lock both affected offerings. Payment expiry/confirmation races are resolved within the same discipline. Locks are held only for the database transaction, never while waiting for a payment provider or a person.

A normal customer reservation succeeds only if its demand fits the freshly calculated capacity and booking rules. Two customers competing for the last unit cannot both pass using an earlier displayed count: the second operation observes the first committed claim before deciding. Promo usage and financial posting apply their own corresponding locks in the overall fixed lock order.

An authorized overbooking request carries the proposed booking change, an explicit acknowledgement of the warning, and a reason. The database verifies the actor's role, re-evaluates the shortage, and ensures the acknowledgement still covers the actual proposed operation and observed deficit. If materially changed, it returns a renewed warning. If accepted, commitment and audit record commit together, recording category, location, dates, quantity, measured capacity/shortfall, actor, time, and reason.

No stored “extra capacity” is created. Customer availability still includes every accepted commitment and remains zero where supply is exhausted. An override authorizes this specific business decision; it does not set a tenant-wide bypass mode.

### 3.4 Structural machine occupancy

MachineOccupancy uses PostgreSQL timestamp-with-timezone ranges and a **GiST exclusion constraint** combining tenant equality, machine equality, and range overlap for blocking records. In plain language: *for the same tenant and machine, no two blocking ranges may intersect*. Rental assignments and maintenance blocks occupy this one relation, so the database compares them against each other. PostgreSQL range exclusion constraints and `btree_gist` directly support this combination. [PostgreSQL range constraints](https://www.postgresql.org/docs/18/rangetypes.html).

All constraint inputs are non-null. Ranges must have a finite lower bound, be nonempty, and use start-inclusive/end-exclusive boundaries. Planned reservations have a finite end. A live rental or explicitly indefinite maintenance block may have an unbounded upper end. Two planned allocations meeting exactly at an endpoint do not overlap; any required turnaround time must be an explicit blocked interval, not hidden pricing arithmetic.

Additional structural checks require exactly one occupancy owner, matching item/machine/tenant context, and at most one blocking rental occupancy per booking item. Allocation dates derive from that item's accepted terms. Releasing/replacing occupancy is an audited operation; changing an item's state cannot disable an occupancy row as a side effect without the required checks. Lifecycle guards reject an assigned/checked-out item lacking its required occupancy/Trip.

Keep the occupancy table unpartitioned in V1. Splitting it by rental date would complicate enforcement across partition boundaries. PostgreSQL requires exclusion constraints on partitioned tables to incorporate the partition keys appropriately; a date partition can otherwise undermine the intended machine-wide comparison. [PostgreSQL partitioning limitations](https://www.postgresql.org/docs/18/ddl-partitioning.html).

The exclusion constraint is the last line of defense, even if application checks are stale. Two simultaneous allocations of the same machine for overlapping intervals cannot both commit. The API maps the conflict to a safe assignment-conflict response without exposing another tenant's record identifiers. Authorized staff may choose another machine or resolve the conflicting work, but cannot force the conflicting row into existence.

### 3.5 Automatic assignment and override

At the tenant's configured lead time, an assignment job locks the relevant offering, item, and candidate machine. It checks the item's current terms and state, current machine category/location/state, maintenance blocks, and occupancy. Candidate ordering is deterministic and based on recorded facts, with a stable fleet identifier tie-breaker; missing engine-hour telemetry is not replaced by zero to rank a machine favorably.

It then inserts occupancy and records assignment in one transaction. The exclusion constraint resolves a race even if another worker found the same candidate. A failed candidate can be followed by another eligible candidate within a bounded retry. Insufficient machines leave the item unassigned with a specific recorded reason and visible unresolved status. Assignment never changes a machine's operational state.

Manual override invokes the same assignment operation with explicit manager/owner authority, replacement choice and reason. It obtains locks in a stable order, validates the replacement, and replaces occupancy atomically. A failed replacement rolls back the entire swap, preserving the previous valid assignment. There is no intermediate committed state in which two customers hold the same machine. Reclassification or transfer cannot be used to evade a conflicting occupancy row because the exclusion key remains the machine identity.

Once a departure has actually happened, replacement hardware cannot be substituted into the existing Trip. A physical handover closes the prior checkout occurrence/Trip with its real boundary observations and creates a distinct checkout occurrence/Trip for the replacement. Both remain linked to the same booking item. The exact permitted state transitions for that operation remain for the next architecture review.

### 3.6 Live custody, late returns, modifications, and maintenance

**Recommended V1 custody policy:** when checkout occurs, the machine's finite planned reservation becomes a live, open-ended occupancy hold. The scheduled return remains in the item's agreed terms for pricing, Today, overdue detection, and category planning. The hard occupancy interval remains open until physical return is recorded.

This deliberately prevents assigning the same machine to a later rental while it is still out. Before opening live custody, the transaction must resolve any later planned machine assignments or maintenance blocks that its open-ended hold would overlap. Later rental items can be atomically reassigned or have their planned assignments released and surfaced as unresolved; their category commitments remain intact. A maintenance block must be explicitly rescheduled/released by an authorized operation or checkout fails. No conflicting maintenance block is silently discarded.

The tradeoff is that automatic assignment cannot firmly reuse a machine that is still physically out, even when it is expected back before the next pickup. That is compatible with assignment shortly before pickup and makes the no-double-handover promise structural in V1. More permissive future planning would require a separate review of custody versus planned allocation semantics; it must not be obtained by weakening the live hold.

Recording return closes the live occupancy at the actual return instant, seals the Trip's core, records the end boundary, and updates the item's state transactionally. Post-rental inspection or incident work can continue independently. No timer, overdue worker, device ignition event, or scheduled return date releases physical custody.

For a pre-checkout date change, the database checks the revised category commitment and replaces the planned occupancy only if it remains feasible; otherwise it chooses another valid machine or records the unresolved assignment condition through the authorized modification path. The transaction also appends terms/price revisions and the financial adjustment journal; failure cannot leave half the change committed.

For an active extension, the current machine remains under its open-ended live hold, while category implications and the revised scheduled return/pricing are checked. Another machine assignment can never be forced through that hold. Overdue status is derived from scheduled return having passed without actual return; there is no automatic late fee. Maintenance uses exactly the same exclusion mechanism as rentals. All these operations preserve historical prices, inspections, Trip bindings, ledger entries, and audit events.

### 3.7 Required proof in the later implementation phase

The architecture's acceptance gate will include real database races and privilege tests covering:

- Two customer reservations for the final category unit: only one normal acceptance; an explicit authorized override is separately required for the other.
- Three eligible machines and four deliberately accepted commitments: four category reservations, at most three overlapping machine assignments, one visible unresolved item.
- Concurrent rental assignments, rental-versus-maintenance blocks, swaps, and interval extensions: no conflicting occupancy can commit.
- A customer still out after scheduled return: live occupancy persists and a second checkout cannot occur on that machine.
- Adjacent interval boundaries, local-date pricing across daylight-saving changes, and fragmented machine eligibility across multiple days.
- Caller attempts to write tables directly, switch tenant/role, exploit an elevated function, read another customer's data, or reuse a pooled session's identity: rejected under actual request roles.
- Duplicate payments, refunds, modifications, messages, and telemetry; callback/backfill ordering; one episode per threshold crossing; and audit failure rolling back its material change.
- Policy/catalog changes, machine transfers, device swaps, and late telemetry after return: old agreements and sealed Trip facts stay unchanged; appended evidence remains attributable.

These are architecture acceptance criteria only, not test code or a test run.
